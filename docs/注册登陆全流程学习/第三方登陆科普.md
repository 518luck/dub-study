# 第三方登录科普

## 1. 第三方登录到底是什么

第三方登录指的是：

- 用户不用在你的网站单独注册账号和密码
- 而是点击 `GitHub 登录`、`Google 登录`
- 跳转到第三方平台授权
- 授权成功后，你的网站再拿到用户身份信息，完成本地登录

注意：

- 这不是“直接拿第三方账号当本地账号”
- 而是“借助第三方证明这个用户是谁”

## 2. 整体流程

以 `GitHub OAuth` 为例，完整流程通常是：

1. 前端点击 `GitHub 登录`
2. 后端/前端跳转到 GitHub 授权页
3. 用户在 GitHub 同意授权
4. GitHub 重定向回你的网站，并附带一个临时 `code`
5. 你的网站后端拿这个 `code` 去请求 GitHub 的 token 接口
6. GitHub 返回 `access_token`
7. 你的网站后端再拿 `access_token` 去请求 GitHub 用户信息接口
8. GitHub 返回该用户的资料，比如 `id`、`login`、`name`、`avatar_url`
9. 你的网站根据这些信息查找或创建本地用户
10. 你的网站再给前端签发自己的登录态，例如 `session` 或 `JWT`

一句话总结：

- `code` 只是中间凭证
- `access_token` 用来请求 GitHub API
- 真正用于你本地登录落库的，通常是用户信息接口返回的数据

## 3. 一开始需要做什么

在正式发起 OAuth 之前，你通常需要先在第三方平台注册应用。

以 GitHub 为例，你需要先创建一个 OAuth App，并拿到：

- `client_id`
- `client_secret`

同时配置：

- `redirect_uri`

这个 `redirect_uri` 很重要，它表示：

- 用户在 GitHub 授权成功后，GitHub 应该把用户带回你网站的哪个地址

例如：

```text
https://your-app.com/api/auth/callback/github
```

## 4. 第一步：跳转到 GitHub 授权页

你的系统会把用户重定向到 GitHub 的授权地址：

```text
GET https://github.com/login/oauth/authorize
```

常见参数有：

- `client_id`
- `redirect_uri`
- `scope`
- `state`

这些参数的作用：

- `client_id`

  - 告诉 GitHub：是哪一个应用在请求授权

- `redirect_uri`

  - 用户授权成功后要跳回哪里

- `scope`

  - 申请哪些权限

- `state`
  - 防止 CSRF 攻击，授权前后要校验是否一致

## 5. 第二步：GitHub 回调时会返回什么

当用户在 GitHub 点击同意后，GitHub 会重定向回你的 `redirect_uri`，并在 URL 上带回：

- `code`
- `state`

这里最关键的是：

- `code`

  - 临时授权码
  - 不是用户信息
  - 不是最终登录态
  - 也不是你本地系统的 token

- `state`
  - 用来校验这次请求是不是你自己发起的

### `code` 的特点

- 是临时的
- 有时效
- 只能用于后端再去换 token

所以：

- 拿到 `code` 后，不能直接认为用户已经登录完成
- 还必须继续请求 GitHub 的 token 接口

## 6. 第三步：拿 `code` 去换 token

你的后端会请求：

```text
POST https://github.com/login/oauth/access_token
```

一般会带上：

- `client_id`
- `client_secret`
- `code`
- `redirect_uri`

### 这一步返回什么

根据 GitHub 官方文档，经典 OAuth App web flow 通常返回：

- `access_token`
- `scope`
- `token_type`

示例：

```json
{
  "access_token": "gho_xxx",
  "scope": "repo,gist",
  "token_type": "bearer"
}
```

注意：

- GitHub 这里官方示例通常没有 `refresh_token`
- 所以不是所有第三方平台都会返回 `refresh_token`

## 7. 第四步：拿 `access_token` 去请求用户信息

这一步才是很多人最容易混淆的地方。

`access_token` 不是主要给前端直接展示用的，而是让你的后端去调用 GitHub API。

例如请求：

```text
GET https://api.github.com/user
Authorization: Bearer ACCESS_TOKEN
```

### 这一接口会返回什么

GitHub 官方文档的示例里，返回的用户信息包括：

- `login`
- `id`
- `node_id`
- `avatar_url`
- `html_url`
- `type`
- `name`
- `company`
- `blog`
- `location`
- `email`
- `bio`
- `twitter_username`
- `created_at`
- `updated_at`

其中最关键的通常是：

- `id`

  - GitHub 那边稳定的用户唯一标识
  - 适合存到本地数据库里的 `providerAccountId`

- `login`

  - GitHub 用户名

- `name`

  - 用户显示名称

- `avatar_url`

  - 用户头像

- `email`
  - 邮箱，但不一定总能拿到

## 8. 为什么不能只靠用户名和头像

因为这些信息不稳定：

- 用户名可能改
- 昵称可能改
- 头像可能换
- 邮箱有时为空，或者以后会变

真正适合标识“这是 GitHub 的哪个用户”的，通常是：

- GitHub 返回的 `id`

所以本地数据库里一般会保存：

- `provider = github`
- `providerAccountId = GitHub 返回的 id`

## 9. 本地系统通常怎么落库

一个常见的做法是：

### 用户表 `User`

保存你系统自己的用户信息，比如：

- 本地 `id`
- `name`
- `email`
- `image`

### 第三方账户绑定表 `Account`

保存：

- `userId`
- `provider`
- `providerAccountId`
- `access_token`
- `scope`
- `token_type`

这样以后用户再用 GitHub 登录时，你就可以通过：

- `provider = github`
- `providerAccountId = xxx`

找到这是不是以前登录过的同一个人。

## 10. 本地登录态是谁发的

很多初学者会误以为：

- GitHub 返回了 `access_token`
- 那前端以后就一直拿这个 GitHub token 当自己网站登录凭证

通常不是这样。

更常见的是：

1. 你的后端拿 GitHub 用户信息完成本地用户识别
2. 然后你自己的系统再签发自己的登录态
3. 前端后续访问你自己的网站时，带的是你自己系统的 `session` 或 `JWT`

所以通常会有两套东西：

- 第三方 token

  - 用于你后端调用 GitHub API

- 本地 token / session
  - 用于用户登录你自己的网站

## 11. `code`、`access_token`、本地登录态 三者区别

### `code`

- GitHub 回调时给你的临时授权码
- 只能短暂使用
- 作用是换 token

### `access_token`

- GitHub 发给你的 API 通行证
- 作用是请求 GitHub 用户信息或其他 API

### 本地 session / JWT

- 你自己系统签发的登录态
- 作用是维持用户在你网站中的登录状态

## 12. 一套最短记忆法

可以直接记成：

1. 跳 GitHub 授权页
2. GitHub 回调带回 `code`
3. 后端用 `code` 换 `access_token`
4. 后端用 `access_token` 请求 GitHub 用户信息
5. 本地创建/查找用户
6. 本地签发自己的登录态

## 13. GitHub 这套流程里分别“返回了什么”

### GitHub 回调给你的网站

返回：

- `code`
- `state`

### token 接口返回

返回：

- `access_token`
- `scope`
- `token_type`

### 用户信息接口返回

返回：

- `id`
- `login`
- `name`
- `avatar_url`
- `email`
- 以及更多 profile 字段

## 14. 这套流程的目的

第三方登录的真正目的不是：

- “把第三方 token 直接塞给前端就结束”

而是：

- 借助 GitHub 证明“这个用户是谁”
- 然后让你的系统完成本地登录

## 15. 常见误区

### 误区 1：`code` 就是 token

不是。

- `code` 是临时授权码
- 要继续换 token

### 误区 2：拿到 token 就已经拿到用户信息

不是。

- token 接口和用户信息接口是两步

### 误区 3：GitHub token 就等于本地登录态

也不是。

- GitHub token 是给 GitHub API 用的
- 本地登录态通常还是你自己系统发

# SSO、OAuth、OIDC、SAML

SSO : 单点登陆体验/目标
OAuth : 授权
OIDC : 在 OAuth 的基础上，增加登录身份层面的能力
SAML : 允许你登录一次，然后访问多个（通常是企业内部的）系统和应用

最容易混的是：
这四个不是同一层概念。

- SSO 是“要达到的效果”
- OAuth / OIDC / SAML 更像“实现方式或协议”

  ## OAuth 是什么

  OAuth 的核心不是登录，而是：

  - 授权一个应用访问另一个系统的资源

  最典型例子：

  - 你的网站想访问 GitHub 上的用户资料
  - 用户同意授权
  - 你的网站拿到 access_token
  - 然后去调用 GitHub API

  所以 OAuth 关注的是：

  - access_token
  - refresh_token
  - scope
  - code
  - 授权流程

  一句话：

  - OAuth = “我允许你访问我的某些数据/资源”

  注意：
  很多人把“GitHub 登录”叫 OAuth 登录，这么说不完全错，但底层更准确地说，单纯 OAuth
  本身更偏授权，不是专门为“身份认证”设计的。

  ## OIDC 是什么

  OIDC = OpenID Connect

  它是在 OAuth 2.0 上加了一层“身份认证”能力。

  也就是说：

  - OAuth 本来只是解决“你能访问什么”
  - OIDC 进一步解决“这个用户到底是谁”

  所以 OIDC 会引入：

  - id_token

  这个 id_token 通常会告诉你：

  - 用户 ID
  - 邮箱
  - 名字
  - 登录身份信息
  - token 签发方
  - 过期时间等

  所以：

  - OAuth 更偏授权
  - OIDC 更偏登录认证

  一句话：

  - OIDC = “在 OAuth 基础上，标准化地告诉你用户身份”

  你现在日常见到的大多数现代“第三方登录”其实更接近：

  - OIDC 登录

  比如很多 Google 登录场景就是这样。

  ## SSO 是什么

  SSO = Single Sign-On
  中文一般叫：单点登录。

  它不是某一个具体协议，而是一种体验/目标：

  - 用户登录一次
  - 多个系统都能用同一个身份登录
  - 不用每个系统再输一遍账号密码

  企业里很常见：

  - 你登录公司身份系统一次
  - Jira、Confluence、Slack、内部后台都认这个登录状态

  所以 SSO 关注的是：

  - 统一身份入口
  - 多系统共享登录体验
  - 企业账号统一管理

  一句话：

  - SSO = “一次登录，多处通行”

  注意这里最重要：

  - SSO 不是协议名
  - 它可以用不同技术实现，比如：
    - OIDC
    - SAML

  ## SAML 是什么

  SAML 是一种比较传统、企业里很常见的单点登录协议。

  全称你现在不用强记，先知道它是：

  - 企业 SSO 的老牌标准协议之一

  典型场景：

  - 公司接入 Okta、Azure AD、OneLogin、Ping Identity
  - 员工登录公司身份系统后访问其他 SaaS
  - 底层很多时候用的就是 SAML

  它和现代 OAuth/OIDC 的感觉不同：

  - 更偏企业级身份对接
  - XML 很多
  - 配置比较重
  - 老牌 SaaS 和企业系统里常见

# 学习prisma

# Prisma schema 语言里的顶层块

- datasource ：定义数据库连接源
  这里的 datasource db { ... } 表示声明一个名叫 db 的数据源。
  - provider = "mysql"：数据库类型是 MySQL
  - url = env("DATABASE_URL")：连接串从环境变量取
  - relationMode = "prisma"：关系约束更多由 Prisma 侧处理，这是这个项目结合
    MySQL/PlanetScale 常见的配置
- generator ：定义 Prisma 要生成什么代码/产物
  这里的 generator client { ... } 表示声明一个名叫 client 的生成器。
  - provider = "prisma-client-js"：生成 JavaScript/TypeScript 用的 Prisma Client
- model ：定义数据模型，也基本对应数据库里的表
  比如 model User { ... }、model Account { ... }、model Session { ... }
  通常可以粗略理解成：
  - 一个 model ~= 一张表
  - 里面的字段 ~= 表的列
  - 关系字段 ~= 表之间的关联

# prisma 的表语法

- model：相当于定义一张表
  id String @id @default(cuid())
  id : 字段名
  String : 类型
  @id : 修饰符
  @default(cuid()) : 修饰符

  所以最基础的格式是：

  字段名 字段类型 字段属性

  ## 常见属性

  @id

  - 表示这个字段是主键
  - 主键的作用是唯一标识一条记录
  - 一张表通常要靠主键区分“每一行是谁”

> 主键就是：一张表里用来唯一标识每一条记录的字段。

@default(...)

- 表示这个字段有默认值
- 当你创建一条记录时，如果没传这个字段，Prisma/数据库会自动给它一个值

@unique

- 这个字段的值不能重复。

# 表理解

1. `User` // 用户
2. `Account` // 账户
3. `Session` // 会话
4. `VerificationToken` // verification 验证核查
5. `EmailVerificationToken`
6. `PasswordResetToken` // reset 重置
7. `Project` // 项目
8. `ProjectUsers`
9. `ProjectInvite` // invite 邀请

这几张表大致分成两组：

- 登录/认证相关：User、Account、Session、各种 Token
- 团队/工作空间相关：Project、ProjectUsers、ProjectInvite

# 表的详细理解

## User

- 这是“人”的主表。
- 表示一个真实用户本身，存放名字、邮箱、头像、密码哈希、是否锁定等信息。
- 在这个项目里，它相当于“账号主体”。

例子：

- 张三注册了 Dub
- 数据库里先有一条 User

## Account

- 这是“登录方式绑定表”，不是“用户本人”。
- 一个用户可以用多种方式登录，比如 GitHub、Google、邮箱登录。
- Account 记录的是：这个 User 绑定了哪个第三方登录提供商。

例子：

- 张三这个 User 用 Google 登录过一次
- 那么会有一条 Account
- 里面会写 provider = "google"，并且指向张三的 userId

所以：

- User = 人
- Account = 这个人绑定的登录渠道

## Session

- 这是“登录状态表”。
- 用户登录成功后，服务端通常会创建一条 session，用来表示“这个用户当前已登录”。
- 里面会有 sessionToken 和过期时间 expires。

例子：

- 张三今天在浏览器登录了
- 数据库里会有一条 Session
- 浏览器后续带着这个 session token，就能识别“这是张三”

所以：

- User 是身份
- Session 是一次登录状态

## VerificationToken

- 这是“登录验证 token”，通常用于无密码登录、magic link 之类场景。
- 用户输入邮箱后，系统发一个一次性 token 给他验证身份。

## EmailVerificationToken

- 这是“邮箱验证 token”。
- 比如用户注册后，需要点邮件里的链接，证明邮箱是自己的。

## PasswordResetToken

- 这是“重置密码 token”。
- 用户忘记密码时，点“找回密码”，系统发一个一次性链接或验证码。

所以这三种 token 可以这样分：

- VerificationToken：验证你是不是要登录
- EmailVerificationToken：验证这个邮箱归你
- PasswordResetToken：允许你重设密码

注意它们都不是长期身份，只是一次性凭证。

## Project

- 这里名字叫 Project，但从字段和关系看，它其实更接近“workspace / 团队空间”。
- 一个 Project 下面有成员、邀请、链接、域名、套餐、用量限制等。
- 也就是“业务容器”。

例子：

- 你创建了一个团队 “Acme”
- 数据库里就是一条 Project
- 这个团队有自己的 slug、套餐、成员、资源配额

所以别被单词 Project 限制住，在这个项目里它更像：

- 工作空间
- 团队
- 组织单元

## ProjectUsers

- 这是“用户和项目的关联表”。
- 因为一个用户可以加入多个项目，一个项目也可以有多个用户，所以需要中间表。
- 这里还记录了用户在项目里的角色，比如 owner、member、viewer、billing。

例子：

- 张三在 Acme 项目里是 owner
- 李四在 Acme 项目里是 viewer
- 那就会有两条 ProjectUsers

所以：

- User 表示人
- Project 表示团队空间
- ProjectUsers 表示“谁属于哪个团队，以及是什么身份”

## ProjectInvite

- 这是“邀请记录表”。
- 当某个项目邀请一个邮箱加入时，先产生邀请，而不是立刻成为成员。
- 只有对方接受邀请后，才可能变成 ProjectUsers 记录。

例子：

- 你邀请 alice@example.com 加入 Acme
- 数据库里先写一条 ProjectInvite
- 等 Alice 接受后，再创建 ProjectUsers

所以：

- ProjectInvite = 尚未生效的邀请
- ProjectUsers = 已经正式加入的成员关系

# 概念 RBAC

RBAC = Role-Based Access Control
典型例子：

- owner
- admin
- member
- viewer

然后不同角色有不同权限：

- owner 可以删除项目、管理成员、改账单
- member 可以正常使用
- viewer 只能看，不能改

# Dub 项目注册登录全流程学习指导

本文基于当前仓库真实代码梳理，重点看 `apps/web` 里的主站 `app.dub.co` 账号体系。  
结论先说清楚：这个项目的“注册”和“创建工作区”是两段式流程。

1. 先注册用户账号。
2. 注册成功后自动登录。
3. 进入 `/onboarding`。
4. 在 onboarding 里再创建 `workspace`。

如果你从 0 学这个项目，建议按下面顺序看，不要一上来就盯着页面组件。

## 一、先建立全局认知

这套认证系统的核心组合是：

1. 前端页面：Next.js App Router 页面 + React 表单组件。
2. 服务端认证：`NextAuth`。
3. 数据库存储：`Prisma + MySQL`。
4. 邮件能力：OTP、登录链接、重置密码邮件。
5. 登录态：`JWT session cookie` 为主，不是数据库 session 为主。

关键入口：

- 认证总配置：`apps/web/lib/auth/options.ts`
- NextAuth 路由：`apps/web/app/api/auth/[...nextauth]/route.tsx`
- 用户/认证表：`packages/prisma/schema/schema.prisma`
- token 表：`packages/prisma/schema/token.prisma`
- 工作区表：`packages/prisma/schema/workspace.prisma`

特别注意：

1. `Session` 表虽然存在，但当前配置是 `session: { strategy: "jwt" }`，实际登录态主要靠 cookie 里的 JWT。
2. 注册成功时只创建 `User`，不会立刻创建 `Project(workspace)`。
3. OAuth 登录和邮箱密码注册共用同一套用户体系。

## 二、按“从 0 搭建”顺序学习

## 第 1 步：先把数据库模型建好

这是整个流程的底座。你先看表，再看接口，否则会乱。

### 你至少要先理解这些表

1.  [x] `User`
2.  [x] `Account`
3.  [x] `Session`
4.  [x] `VerificationToken`
5.  [x] `EmailVerificationToken`
6.  [x] `PasswordResetToken`
7.  [ ] `Project`
8.  [ ] `ProjectUsers`
9.  [ ] `ProjectInvite`

对应源码：

- `packages/prisma/schema/schema.prisma`
- `packages/prisma/schema/token.prisma`
- `packages/prisma/schema/workspace.prisma`

### 每张表在流程里的职责

1. `User`
   存账号主体，重点字段是 `email`、`passwordHash`、`emailVerified`、`invalidLoginAttempts`、`lockedAt`、`defaultWorkspace`。
2. `Account`
   存 OAuth 账号映射，比如 Google、GitHub。
3. `Session`
   NextAuth 兼容表；当前项目主要不是靠它维持登录态。
4. `VerificationToken`
   给 NextAuth 的邮箱登录链接用。
5. `EmailVerificationToken`
   给注册时的 6 位 OTP 验证码用。
6. `PasswordResetToken`
   给忘记密码流程用。
7. `Project`
   也就是 workspace，本项目注册后要创建的业务空间。
8. `ProjectUsers`
   用户和 workspace 的关联表，表示用户在某个 workspace 里的角色。
9. `ProjectInvite`
   workspace 邀请成员时使用。

### 注意点

1. 注册流程最核心的不是只建 `User`，而是提前把验证码、密码重置、OAuth 关系都考虑好。
2. 这个项目把“用户身份”和“工作区身份”拆开了，后面权限判断基本都靠 `ProjectUsers`。
3. `defaultWorkspace` 很关键，它决定登录后默认进哪个工作区。

## 第 2 步：先把 NextAuth 主配置立起来

只有把认证“总开关”看明白，后面前后端调用才串得起来。

核心文件：

- `apps/web/lib/auth/options.ts`
- `apps/web/app/api/auth/[...nextauth]/route.tsx`

### 这个项目接了哪些登录方式

1. `EmailProvider`
   邮箱登录链接。
2. `CredentialsProvider`
   邮箱 + 密码登录。
3. `GoogleProvider`
4. `GithubProvider`
5. `SAML`
6. `Framer OAuth`

### 这里要重点看什么

1. `providers`
   决定前端能发起哪些登录方式。
2. `adapter: PrismaAdapter`
   负责把 NextAuth 和 Prisma 接起来。
3. `callbacks.signIn`
   登录成功前的二次校验和附加逻辑。
4. `callbacks.jwt`
   把用户信息写进 JWT。
5. `callbacks.session`
   把 JWT 中的用户信息挂到 `session.user`。
6. `events.signIn`
   新用户登录后触发欢迎流程和埋点。

### 注意点

1. 当前项目把 cookie 域做了跨子域处理，生产环境下能支持不同子域共享认证。
2. `callbacks.signIn` 不只是“成功就放行”，里面还有黑名单邮箱、SAML 强制登录、Framer 特殊限制。
3. `createUser` 被自定义过，创建用户时会额外创建 `notificationPreferences`。

## 第 3 步：先实现注册页面前端

先看前端交互，再去看后端 action，会更容易理解。

核心文件：

- `apps/web/app/app.dub.co/(auth)/register/page.tsx`
- `apps/web/app/app.dub.co/(auth)/register/page-client.tsx`
- `apps/web/ui/auth/register/signup-form.tsx`
- `apps/web/ui/auth/register/signup-email.tsx`
- `apps/web/ui/auth/register/signup-oauth.tsx`
- `apps/web/ui/auth/register/context.tsx`

### 前端做了什么

1. 页面先进入 `signup` 阶段。
2. 用户可以选邮箱注册，也可以直接点 Google/GitHub。
3. 邮箱注册时，先输入邮箱。
4. 如果用户继续提交，再显示密码框。
5. 提交后不是直接建用户，而是先发送 OTP。
6. OTP 成功发送后，切到 `verify` 阶段。

### 你在自己搭这一步时要先做什么

1. 先做注册页状态机。
2. 至少区分两个状态：`signup` 和 `verify`。
3. 把 `email`、`password` 暂存在前端上下文里。
4. 前端要先做表单校验，再调用后端。

### 注意点

1. 这里不是“一个表单一次提交结束”，而是两阶段注册。
2. 密码规则比较严格：至少 8 位，且必须包含数字、小写、大写。
3. 注册页的 OAuth 按钮本质上直接调用 `next-auth/react` 的 `signIn("google")` / `signIn("github")`。

## 第 4 步：后端先做“发送注册验证码”

这一步对应邮箱注册的第一段后端逻辑。

核心文件：

- `apps/web/lib/actions/send-otp.ts`
- `apps/web/lib/zod/schemas/auth.ts`
- `apps/web/lib/auth/constants.ts`

### 后端做了什么

1. 校验邮箱和密码格式。
2. 检查当前用户是否已经登录，已登录则不允许走注册。
3. 对 `send-otp` 做限流。
4. 检查邮箱是否合法。
5. 检查是否是一次性邮箱、黑名单邮箱域、`+` 泛型邮箱等。
6. 检查这个邮箱是否已经注册过。
7. 生成 6 位 OTP。
8. 删除旧的 `EmailVerificationToken`。
9. 新建一条新的 `EmailVerificationToken`。
10. 发验证邮件。

### 这一步涉及的表

1. `User`
   用来检查是否已存在用户。
2. `EmailVerificationToken`
   用来保存当前注册验证码。

### 注意点

1. OTP 过期时间是 5 分钟。
2. 同一个邮箱旧验证码会被删除，只保留最新的一条。
3. 这里还没有建用户，建用户在下一步。

## 第 5 步：后端再做“校验 OTP 并真正创建用户”

这是注册流程最核心的一步。

核心文件：

- `apps/web/lib/actions/create-user-account.ts`
- `apps/web/lib/auth/password.ts`

### 后端做了什么

1. 校验 `email`、`password`、`code`。
2. 对连续输错 OTP 的行为做限流和锁定。
3. 去 `EmailVerificationToken` 表查验证码是否存在。
4. 检查验证码是否过期。
5. 验证通过后删除验证码。
6. 查 `User` 是否已经存在。
7. 如果不存在，则创建用户。
8. 创建时写入：
   `email`、`passwordHash`、`emailVerified`、`notificationPreferences`。

### 这一步在数据库层真正落了什么

1. 新增 `User`
2. 删除 `EmailVerificationToken`

### 注意点

1. 密码不是明文存储，使用 `bcryptjs`，`hash(password, 12)`。
2. 注册成功时直接把 `emailVerified` 标成当前时间，因为 OTP 已经验证过邮箱了。
3. 这一步仍然没有创建 workspace。

## 第 6 步：前端注册成功后，自动登录并跳转 onboarding

这一段非常重要，因为它解释了为什么注册后不是直接进业务页。

核心文件：

- `apps/web/ui/auth/register/verify-email-form.tsx`

### 前端做了什么

1. `createUserAccountAction` 成功后弹成功提示。
2. 立即调用 `signIn("credentials")` 自动用邮箱密码登录。
3. 如果登录成功，跳转到 `/onboarding`。
4. 如果 URL 里有 `next`，会尽量保留这个跳转参数。

### 注意点

1. 自动登录用的是刚才输入的邮箱和密码，不会再让用户重复输入一次。
2. 真正的“首次业务初始化”不是在注册 action 里做，而是在后面的 onboarding 里做。

## 第 7 步：再看登录页面前端

注册看完后，再看登录会很顺。

核心文件：

- `apps/web/app/app.dub.co/(auth)/login/page.tsx`
- `apps/web/ui/auth/login/login-form.tsx`
- `apps/web/ui/auth/login/email-sign-in.tsx`
- `apps/web/ui/auth/login/google-button.tsx`
- `apps/web/ui/auth/login/github-button.tsx`

### 这个登录页的设计思路

它不是直接展示一个固定的“邮箱 + 密码”表单，而是先判断这个账号适合哪种登录方式。

### 前端实际流程

1. 用户先输入邮箱。
2. 前端先调用 `checkAccountExistsAction`。
3. 后端返回：
   `accountExists`、`hasPassword`、`requireSAML`。
4. 如果企业邮箱要求 SAML，则提示走企业 SSO。
5. 如果账号存在且有密码，则展示密码输入框。
6. 如果账号存在但没密码，允许走邮箱登录链接。
7. 如果输入了密码，则走 `signIn("credentials")`。
8. 如果没输入密码，则走 `signIn("email")` 发登录链接。

### 注意点

1. 这个项目把“账号探测”和“真正登录”分成了两段。
2. 一个邮箱可能既支持密码登录，也支持邮箱链接登录。
3. 前端会记住用户上次使用的登录方式，存到 `localStorage`。

## 第 8 步：后端实现登录校验

登录前端只是在收集输入，真正的身份校验都在 NextAuth provider 里。

核心文件：

- `apps/web/lib/actions/check-account-exists.ts`
- `apps/web/lib/auth/options.ts`

### `checkAccountExistsAction` 做什么

1. 校验邮箱格式。
2. 限流。
3. 查询 `User` 是否存在。
4. 判断这个用户是否有 `passwordHash`。
5. 判断邮箱域是否强制 SAML。

### `CredentialsProvider.authorize` 做什么

1. 校验邮箱和密码是否传了。
2. 对登录尝试做限流。
3. 判断是否强制走 SAML。
4. 查询用户。
5. 检查是否有密码。
6. 检查是否超过登录失败次数。
7. 用 bcrypt 校验密码。
8. 密码错了就递增 `invalidLoginAttempts`。
9. 邮箱没验证过则拒绝登录。
10. 登录成功后清空失败次数。

### 登录失败控制

相关字段在 `User` 表里：

1. `invalidLoginAttempts`
2. `lockedAt`

### 注意点

1. 这套逻辑不是简单“账号密码查库”。
2. 它把限流、锁定、SAML 强制、邮箱验证状态都揉进来了。
3. 如果你自己复刻这个流程，登录失败计数一定要放在后端。

## 第 9 步：邮箱登录链接、OAuth 登录也要一起理解

这个项目不是只有账号密码。

### 邮箱登录链接

入口还是登录页，只是最终调用的是 `signIn("email")`。

后端依赖：

1. `EmailProvider` in `apps/web/lib/auth/options.ts`
2. `VerificationToken` 表

作用：

1. NextAuth 自动生成登录链接。
2. 邮件里发给用户。
3. 用户点开后完成登录。

### OAuth 登录

入口文件：

- `apps/web/ui/auth/register/signup-oauth.tsx`
- `apps/web/ui/auth/login/google-button.tsx`
- `apps/web/ui/auth/login/github-button.tsx`

后端依赖：

1. `GoogleProvider`
2. `GithubProvider`
3. `Account` 表

作用：

1. 首次 OAuth 登录时，NextAuth 会创建或关联用户。
2. 第三方账号关系写入 `Account`。
3. 新用户仍然会在后续中间件里被导向 onboarding。

### 注意点

1. OAuth 首登和邮箱注册虽然入口不同，但最后都归到同一张 `User` 表。
2. 账号体系设计的关键不是入口统一，而是“落库身份统一”。

## 第 10 步：注册后真正的业务初始化是创建 workspace

这是这个项目和很多简单 demo 最大的不同点。

核心文件：

- `apps/web/app/api/workspaces/route.ts`
- `apps/web/ui/workspaces/create-workspace-form.tsx`

### 真实流程

1. 用户注册成功。
2. 自动登录。
3. 中间件发现这是新用户、还没有默认 workspace。
4. 重定向到 `/onboarding`。
5. 用户在 onboarding 中填写 workspace 信息。
6. 前端 POST `/api/workspaces`。
7. 后端创建 `Project`。
8. 同时创建 `ProjectUsers`，把当前用户设为 `owner`。
9. 如果用户还没有 `defaultWorkspace`，就把这个新 workspace 设成默认。

### 这一步为什么重要

因为 Dub 是多 workspace 产品。  
用户能登录，不代表他已经拥有一个可以工作的业务空间。

### 这一步至少涉及哪些表

1. `Project`
2. `ProjectUsers`
3. `User.defaultWorkspace`

### 注意点

1. workspace 创建使用事务，避免部分成功。
2. slug 冲突在后端兜底处理。
3. 这个阶段才是真正把账号接到业务系统上。

## 第 11 步：中间件负责把整个流程串起来

如果只看页面和接口，你会漏掉“为什么页面会自动跳转”。

核心文件：

- `apps/web/lib/middleware/app.ts`

### 中间件做了什么

1. 未登录访问受保护页面时，重定向到 `/login`。
2. 已登录但还是新用户、没有 workspace、onboarding 未完成时，重定向到 `/onboarding`。
3. 已登录且已有默认 workspace 时，跳到默认 workspace。

### 这一步在流程中的意义

它是整个注册登录流程的“交通警察”。

### 注意点

1. 很多“看起来像页面自己决定的跳转”，其实是中间件决定的。
2. 学这个项目时，一定要把页面逻辑和中间件逻辑分开看。

## 第 12 步：补上忘记密码和重置密码

登录注册流程完整闭环，必须把密码找回一起看。

核心文件：

- `apps/web/app/app.dub.co/(auth)/forgot-password/page.tsx`
- `apps/web/ui/auth/forgot-password-form.tsx`
- `apps/web/lib/actions/request-password-reset.ts`
- `apps/web/app/api/auth/reset-password/route.ts`

### 忘记密码流程

1. 前端提交邮箱。
2. 后端检查用户是否存在。
3. 若存在，删除旧 `PasswordResetToken`。
4. 新建新的 `PasswordResetToken`。
5. 发送重置密码邮件。

### 重置密码流程

1. 用户点邮件链接，进入 reset 页面。
2. 前端把新密码和 token 提交到 `/api/auth/reset-password`。
3. 后端校验 token 是否存在且未过期。
4. 校验新密码不能和旧密码一致。
5. 删除 token。
6. 更新 `passwordHash`。
7. 清空 `lockedAt`。
8. 如果之前邮箱还没验证过，顺手把 `emailVerified` 补上。

### 注意点

1. `PasswordResetToken` 有效期是 1 小时。
2. 密码重置成功后会自动解锁账号。
3. 这条链路也会发送“密码已更新”的通知邮件。

## 三、按时序再串一次真实运行流程

## 场景 A：邮箱注册

1. 前端打开 `/register`。
2. 输入邮箱和密码。
3. 调 `sendOtpAction`。
4. 后端写 `EmailVerificationToken` 并发邮件。
5. 前端切到验证码页。
6. 用户输入 OTP。
7. 调 `createUserAccountAction`。
8. 后端校验 OTP，创建 `User`。
9. 前端自动 `signIn("credentials")`。
10. NextAuth 签发 session cookie。
11. 中间件把用户导向 `/onboarding`。
12. 用户创建 workspace。
13. 后端创建 `Project + ProjectUsers`。
14. 用户真正进入业务系统。

## 场景 B：邮箱登录

1. 前端打开 `/login`。
2. 输入邮箱。
3. 调 `checkAccountExistsAction`。
4. 如果有密码，显示密码框。
5. 调 `signIn("credentials")`。
6. NextAuth 走 `CredentialsProvider.authorize`。
7. 校验成功后返回 session。
8. 中间件根据默认 workspace 决定落点。

## 场景 C：邮箱链接登录

1. 前端打开 `/login`。
2. 输入邮箱。
3. 账号存在但用户不输密码，或账号本来就没有密码。
4. 调 `signIn("email")`。
5. NextAuth 创建 `VerificationToken` 并发登录链接邮件。
6. 用户点邮件链接完成登录。

## 场景 D：OAuth 登录

1. 前端点 Google/GitHub。
2. 跳第三方授权。
3. NextAuth 回调。
4. 写入/关联 `User + Account`。
5. 回到站内后，中间件判断是否要去 onboarding。

## 五、你自己实现时最容易踩的坑

1. 不要把“注册用户”和“创建业务空间”混在一个接口里，这个项目是拆开的。
2. 不要只建 `User` 表，验证码和重置密码 token 表必须提前设计。
3. 不要把登录失败次数放前端控制，必须后端落库或至少后端限流。
4. 不要把所有登录方式都硬塞成一套表单，先判断账号适合的登录方式，用户体验更好。
5. 不要忽略中间件，它决定了注册后、登录后、未登录时分别被送去哪里。
6. OAuth 登录完成后也要走统一用户落库，不要单独搞另一套用户表。
7. workspace 是业务权限核心，真正的资源权限判断不要只看 `User`，要看 `ProjectUsers`。

## 六、这一套流程最关键的设计思想

1. 账号身份和业务空间分离。
2. 注册、登录、找回密码、OAuth、SSO 共用同一用户底座。
3. 页面只负责采集输入，真正认证判断放在服务端。
4. 中间件负责流程编排。
5. onboarding 负责把“有账号”变成“可进入业务系统的用户”。

如果你下一步要继续深入，建议直接从 `apps/web/lib/auth/options.ts` 开始，随后顺着“注册 action -> 自动登录 -> middleware -> onboarding -> /api/workspaces”这条链一路读下去，最容易建立完整认知。

# 中型项目结构原则

这份笔记不是在总结某一个语法点，而是在总结：

- 怎么看一个像 `dub` 这样的中型到中大型前端项目
- 这种项目的结构为什么会长成这样
- 我现在该学什么，不该急着学什么
- 怎么判断自己是真的学会了，而不是“看懂了一点”

---

## 1. 先判断：`dub` 属于什么类型的项目

`dub` 不是教学 demo，也不是简单官网。

更接近：

- 中型到中大型 SaaS Web App
- 带后台控制台属性的真实业务项目
- 有较强工程分层、业务分层和复用意识的 Next.js 项目

从仓库结构上看，它至少有这些层面：

- `apps/web/app`
  路由、页面、layout、API route
- `apps/web/ui`
  业务 UI 组件
- `apps/web/lib`
  数据获取、业务逻辑、server action、API 封装、认证、中间件等
- `packages/ui`
  通用 UI 组件和 hooks
- `packages/utils`
  通用工具函数
- `packages/prisma`
  数据模型/schema

这说明它不是“单纯页面项目”，而是已经有明显的：

- 应用层
- 业务层
- 通用组件层
- 通用工具层
- 数据/模型层

这就是中型项目最典型的特征之一：

不是代码很多而已，而是开始出现明确分层。

---

## 2. 中型项目最重要的结构原则

看中型项目时，优先判断下面这 5 件事。

### 2.1 哪些是全局的

全局层通常包括：

- 根 layout
- 全局样式
- providers
- 全局脚本
- 全局认证上下文
- 全局 modal / toast / theme

在这个项目里，对应典型位置：

- `apps/web/app/layout.tsx`
- `apps/web/app/providers.tsx`
- `apps/web/app/app.dub.co/layout.tsx`

要训练自己的问题意识：

- 这段代码是全站都需要的吗
- 还是只在某个子应用需要
- 还是只在某组页面需要

### 2.2 哪些是模块级的

模块级指的是：

- 它不是全局
- 但它也不是某一个页面私有
- 它属于某个业务域或布局域

比如：

- `layout/sidebar`
- `layout/toolbar`
- `analytics`
- `partners`
- `modals`

中型项目通常会开始按功能域建目录，而不是只按文件类型堆在一起。

### 2.3 哪些是通用能力

通用能力一般放到共享层，典型包括：

- 通用 hooks
- 通用 UI 组件
- 工具函数
- 通用请求封装

在这个项目里典型是：

- `packages/ui/src/hooks`
- `packages/ui/src/icons`
- `packages/utils/src/functions`

判断标准：

- 这段逻辑是否和某个具体业务强耦合
- 如果换一个页面/业务，还能不能继续用

### 2.4 哪些是业务耦合代码

业务耦合代码通常会和产品概念强绑定，比如：

- `workspace`
- `billing`
- `onboarding`
- `partners`
- `program`
- `payouts`
- `fraud`

这些不是“通用前端概念”，而是产品业务概念。

这类代码通常不需要为了“抽象优雅”而强行拆成通用库。

### 2.5 哪些该抽，哪些可以先放一起

这是工程感的核心。

该抽的典型情况：

- 一段逻辑重复了两次以上
- 职责单一
- 名字能说清楚
- 别处也大概率会用

可以先放一起的典型情况：

- 高度业务耦合
- 暂时只用一次
- 强行抽出来只会制造更多跳转成本

要记住：

工程感不是“拆得越细越好”，而是“拆得有收益”。

## 3. 这类项目为什么难读

这种项目难读，主要不是因为语法，而是因为下面几层复杂度叠在一起了。

### 3.1 业务复杂度

难点不只是 React，而是业务词本身：

- workspace
- billing
- upgrade
- onboarding
- referrals
- partner program

这些如果不理解业务含义，代码会显得很重。

### 3.2 工程分层复杂度

Next.js App Router 项目会有：

- 多层 `layout.tsx`
- route groups
- server component / client component
- route handlers
- providers

这对刚开始读真实项目的人不算轻。

### 3.3 共享层复杂度

像下面这些一旦存在，改动影响面就会增大：

- sidebar
- toolbar
- modal provider
- session provider
- workspace 切换
- plan 能力判断

### 3.4 真实项目不是按教学顺序写的

真实项目写法的优先级通常是：

- 可维护
- 可复用
- 团队协作
- 支撑业务迭代

不是“让新手第一次看最容易懂”。

## 4. 这种项目里最值得学的，不是某个目录，而是分层思维

不要试图背目录。

要学的是下面这些思维。

### 4.1 layout 思维

layout 解决的是：

- 哪些页面共享同一个壳子
- 哪些组件应该放在哪一层
- 作用范围该控制在哪里

在这个项目里典型分成：

- `app/layout.tsx`
  全站壳
- `app/app.dub.co/layout.tsx`
  子应用壳
- `app/app.dub.co/(dashboard)/layout.tsx`
  dashboard 壳

### 4.2 组件职责思维

一个组件至少要先判断它更偏哪类：

- 布局壳子
- 业务组件
- 通用组件
- 展示组件
- 数据装配组件

比如：

- `MainNav`
  更像布局壳子
- `AppSidebarNav`
  更像业务装配组件
- `useLocalStorage`
  更像通用 hook

### 4.3 数据与渲染分离思维

读大文件时，先粗分成三块：

- 配置
- 数据
- 渲染

比如 `app-sidebar-nav.tsx` 就明显混了：

- 导航配置
- 计数数据
- 当前 area 判断
- 最终 `SidebarNav` 渲染

先看出这三块，比逐行看更重要。

### 4.4 作用域思维

任何代码都在某个作用域里：

- 全站
- 子应用
- 页面组
- 模块
- 组件
- 单次交互

很多“为什么放这里不放那里”的问题，本质上都在问作用域。

## 5. 我现在到底应该学什么

不要全学。

优先级应该非常明确。

### 第一层：必须先学的基础

这是最重要的底座。

#### React / Next.js 基础

至少要能顺着看懂：

- 组件
- `props`
- `children`
- `useState`
- `useEffect`
- context
- 自定义 hook
- `layout.tsx`
- `page.tsx`
- client/server component 的基本区别

#### TypeScript 基础读法

维护项目先是“看懂 TS”，不是“炫 TS”。

至少要能看懂：

- `type` / `interface`
- 联合类型
- 泛型基础
- `as const`
- `typeof xxx`
- 可选链 `?.`
- 空值合并 `??`
- 数组/对象解构

#### CSS / Tailwind 基础

至少要能看懂：

- `flex`
- `grid`
- 定位
- 响应式断点
- `overflow`
- 常见 Tailwind class

### 第二层：项目阅读能力

这一层是你现在最该练的。

要练会：

- 从页面反找代码
- 从组件反找上层布局
- 看一个文件先判断职责
- 顺着 props 往下追
- 顺着 hook 往里追
- 大文件先分块

### 第三层：基本工程感

至少要有下面这些意识：

- 公共逻辑不要乱复制
- layout 和 page 分开
- 不要为了抽象而抽象
- 局部修改优先
- 命名直白比炫技重要
- 作用范围越大，改动越要谨慎

### 第四层：真实业务理解能力

要慢慢能回答：

- 这个按钮为什么显示
- 这个 banner 为什么在这里
- 这个 session/provider 为什么放这一层
- 这个页面为什么是这个 layout
- 这个 hook 为什么存在

这才是维护中型项目的核心。

## 6. 我不应该急着学什么

很多人容易走偏，主要是因为学得太散、太早追求高级感。

下面这些不要太早沉迷。

### 6.1 不要太早追求“高级架构名词”

比如：

- 微前端
- DDD
- 企业级架构
- 高级状态管理模型

先把一个真实项目的局部读明白，比背这些更重要。

### 6.2 不要太早追求“极致抽象”

比如刚做 MVP 就：

- 抽十层 hooks
- 造超级通用组件
- 为未来 100 个页面设计今天的 3 个页面

这不叫工程感，这叫过度设计。

### 6.3 不要把“会看大项目”等同于“什么都得会”

你现在不需要同时深入：

- 电商
- 社区
- 内容平台
- 云平台
- 编辑器平台

先吃透一类项目的通用规律就够了。

## 7. 我该怎么学这个项目

核心原则：

- 不要通读
- 不要扫目录
- 不要先挑战最大文件
- 要沿着界面和问题读

### 7.1 最好的读法：界面驱动

看到页面上的一个部分，就问：

- 这个区域对应哪个组件
- 这个组件在哪一层被挂载
- 它为什么在这一层
- 数据从哪来

这是最适合初中级开发的读法。

### 7.2 一次只读一条链路

例如：

- `layout.tsx -> MainNav -> AppSidebarNav -> SidebarNav`
- `Toolbar -> OnboardingButton`
- `UpgradeBanner -> useUpgradeBannerVisible`

每次只搞清楚一条链路，不要同时横跳太多模块。

### 7.3 大文件先分块，不逐行硬啃

看到一个 600 行文件，先只做这件事：

- 这文件的核心职责是什么
- 里面有哪几块
- 哪块是配置
- 哪块是数据
- 哪块是渲染

如果这一步都没做，就直接逐行读，效率会很差。

### 7.4 先理解“负责什么”，再理解“怎么实现”

顺序一定要对。

错误顺序：

- 一上来就抠 every line 的语法

更好的顺序：

- 先知道它干什么
- 再知道为什么这样放
- 最后再看实现细节

## 8. 针对 `dub` 这种项目，一个更实际的学习路线

### 阶段 1：只看壳子

目标：

- 知道页面是谁包谁
- 知道 layout 为什么分层
- 知道 `children` 最后落在哪

推荐先看：

- `apps/web/app/layout.tsx`
- `apps/web/app/app.dub.co/layout.tsx`
- `apps/web/app/app.dub.co/(dashboard)/layout.tsx`
- `apps/web/ui/layout/main-nav.tsx`

### 阶段 2：只看一个布局模块

目标：

- 知道侧边栏、toolbar、banner 的关系

推荐顺序：

- `main-nav.tsx`
- `toolbar/toolbar.tsx`
- `upgrade-banner.tsx`
- `sidebar/app-sidebar-nav.tsx`

### 阶段 3：只看小 hook

目标：

- 理解为什么真实项目要抽小逻辑

推荐：

- `packages/ui/src/hooks/use-local-storage.ts`
- `packages/ui/src/hooks/use-media-query.ts`

### 阶段 4：顺着一个功能走完整闭环

比如：

- onboarding 按钮为什么显示
- help 按钮为什么出现
- 移动端侧边栏怎么打开关闭

### 阶段 5：开始自己做小改动

这一步很关键。

只看不改，成长很慢。

适合的改动包括：

- 给现有组件补注释
- 调整一个 class 的含义
- 把一个判断提成更清楚的变量名
- 给某个小区域加一个简单 UI 变化

## 9. 学这种项目时最需要注意什么

### 9.1 不要追求“完全理解全局”

这几乎不现实。

真实工作也不是要求你先全懂再动手，而是：

- 足够理解当前链路
- 能安全改局部

### 9.2 不要把每个语法点都卡死

像：

- `as const`
- `typeof xxx`
- `[number]`
- `??`

这些当然要懂，但不要因为它们阻塞整条业务链路。

更好的做法是：

- 单独做语法笔记
- 项目链路先继续读

### 9.3 不要因为大文件就否定自己

大文件很多时候不是你水平不够，而是：

- 配置太长
- 业务堆积
- 还没来得及拆

你要先学会“读大文件的方法”，而不是一见大文件就怀疑人生。

### 9.4 不要把“能解释代码”误判成“能维护项目”

能解释只是第一步。

真正的维护能力还包括：

- 会改
- 会验证
- 会控影响面
- 会跟现有结构协作

### 9.5 不要盲目照搬成熟项目结构做 MVP

`dub` 适合拿来学分层，不适合整套照抄做小项目。

MVP 需要的是：

- 够用
- 可迭代
- 不乱

不是：

- 一开始就长成成熟 SaaS

## 10. 怎么验证自己是真的学会了

这是最重要的部分。

如果不能验证，学习就很容易变成“自我感觉良好”。

### 10.1 第一层验证：能复述

你至少要能自己说清楚：

- 这个文件是干什么的
- 这个组件为什么放在这里
- 这个 hook 在封装什么
- 这个 layout 的作用范围是什么

如果不能用自己的话讲清楚，通常还不算真正理解。

### 10.2 第二层验证：能定位

给自己出题：

- 页面左侧导航从哪里进来
- onboarding 为什么会显示
- 顶部横幅为什么会影响布局高度
- help 按钮在哪里挂进去

如果你能不靠别人直接找到代码路径，说明开始具备项目阅读能力。

### 10.3 第三层验证：能做小改动

这是最关键的验证。

例如：

- 给一个组件加一条合理注释
- 修改一个展示条件
- 调整一个按钮文案
- 调整一个简单布局

如果你能改对并解释为什么这样改，理解才开始变实。

### 10.4 第四层验证：能预测影响面

改动前先问自己：

- 这个组件是不是公共组件
- 哪些页面可能一起受影响
- 这个状态是不是别的地方也在用

能预测影响面，才算开始有工程感。

### 10.5 第五层验证：能独立写一个类似但更小的模块

这是更高一级的验证。

比如你能模仿这个项目做一个小型模块：

- 一个双列 layout
- 一个 sidebar + content
- 一个 toolbar
- 一个小 hook

不要求一模一样，但要求你知道为什么要这么分。

## 11. 什么才算“我已经具备了维护中型项目的基础”

不是“我会背多少 API”，而是你已经能做到下面这些。

### 我能读

- 能顺着页面找到主要组件
- 能看懂常见 React / TS 写法
- 能分清布局组件、业务组件、通用 hook

### 我能改

- 能在现有项目里做小功能改动
- 能修简单 bug
- 能跟着现有结构写代码

### 我能判断

- 能判断一段逻辑该不该抽
- 能判断改动放哪一层更合理
- 能判断影响范围

### 我能验证

- 知道在哪看效果
- 能做基本自测
- 能解释自己改动的原因

如果这四个“能”开始成立，就已经不是只会看教程的状态了。

---

## 12. 迁移能力到底是什么

迁移能力不是“把这个项目背熟”。

而是：

以后换一个陌生项目，你仍然知道该怎么看。

真正可迁移的是这些能力：

- 看一个目录先判断它按什么维度拆分
- 看一个组件先判断职责
- 看一个大文件先分块
- 看一个 layout 先判断作用范围
- 看一个 hook 先判断它封装了什么逻辑
- 改代码前先想影响面

这就是为什么学习 `dub` 有价值。

不是因为以后所有项目都长这样，
而是因为你可以借它练出“读真实项目”的方法。

---

## 13. 最后给自己的执行标准

以后学一个新项目，不要问：

- 我什么时候能全看完

应该问：

### 第一步

- 我能不能先画出这个项目的大致地图

### 第二步

- 我能不能顺着一个页面走通一条链路

### 第三步

- 我能不能解释 1 到 2 个核心组件为什么这么设计

### 第四步

- 我能不能做一个不破坏结构的小改动

### 第五步

- 我能不能从这个项目提炼出可迁移的方法

---

## 一句话总结

学习 `dub` 这种中型项目，真正要学的不是“把所有代码看完”，而是：

- 学会分层
- 学会判断职责
- 学会顺着界面定位代码
- 学会在不全懂全局的情况下安全修改局部
- 学会把这些方法迁移到下一个陌生项目

这才是能真正带走的能力。
